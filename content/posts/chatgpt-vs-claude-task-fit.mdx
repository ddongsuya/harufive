ChatGPT와 Claude 중에 무엇을 써야 하느냐는 질문은 생각보다 오래 붙잡습니다. 검색해 보면 비교 글이 넘치는데, 읽고 나서도 결정이 안 되는 이유는 대개 세 가지입니다. 첫째, 결론이 특정 버전의 특정 과제에서 나온 것이라 몇 달이면 낡습니다. 둘째, 벤치마크 점수는 내 업무에 있는 사내 용어와 표 형식, 보고서 문체를 반영하지 않습니다. 셋째, 두 도구 모두 "잘한다"는 말이 사실이라서, 잘한다는 것만으로는 고르는 기준이 되지 못합니다.

그래서 이 글은 "어느 쪽이 더 낫다"로 끝내지 않습니다. **두 도구가 구조적으로 갈리는 지점을 먼저 잡고, 내 업무 세 개로 직접 재는 절차를 정리**합니다. 한 번 재 두면 그다음부터는 비교 글을 다시 읽지 않아도 됩니다.

## 비교 글이 금방 낡는 이유

AI 도구 비교에서 가장 빨리 쓸모없어지는 정보는 모델 이름과 성능 순위입니다. 반대로 오래 가는 정보는 **일하는 방식의 차이**입니다. 대화를 어떻게 이어 가는지, 파일을 어떻게 넣는지, 외부 시스템과 무엇으로 연결하는지, 결과물을 어떤 형태로 꺼내는지. 이 네 가지는 모델이 바뀌어도 큰 틀이 잘 흔들리지 않습니다.

비교 글을 읽을 때는 결론보다 근거를 보세요. "A가 코드를 더 잘 쓴다"보다 "A는 저장소 전체를 읽고 고치고, B는 대화에 붙여 넣은 코드를 다룬다"가 내 상황에 쓸 수 있는 문장입니다. 앞의 문장은 다음 버전에서 뒤집힐 수 있지만, 뒤의 문장은 내가 무엇을 준비해야 하는지를 알려 줍니다.

<Callout type="note" title="기능 이름과 한도는 자주 바뀝니다">
아래 표는 2026년 11월 기준으로 두 서비스가 공개하고 있는 구조를 정리한 것입니다. 요금제 이름, 메시지 한도, 모델 목록, 연동 기능은 몇 달 단위로 바뀝니다. 실제로 결제하거나 팀에 도입하기 전에는 각 서비스의 공식 도움말에서 같은 항목을 다시 확인하세요. 이 글에서는 바뀌기 쉬운 숫자를 단정하지 않고 확인 항목으로 적었습니다.
</Callout>

## 구조적으로 갈리는 네 지점

| 항목 | ChatGPT | Claude | 내 업무에서 확인할 것 |
| --- | --- | --- | --- |
| 확장 방식 | GPTs, 앱 연동과 커넥터로 기능을 붙임 | MCP라는 연결 규격을 열어 두고, 개발 도구와 함께 쓰는 쪽이 강함 | 사내 시스템이나 반복 작업을 붙일 계획이 있는가 |
| 코드 작업 | 대화 안에서 코드 작성·실행, 저장소 작업을 맡기는 흐름 | 터미널·에디터에서 도는 코딩 에이전트 비중이 큼 | 파일 하나를 고치는가, 저장소 전체를 다루는가 |
| 문서 작업 | 파일 업로드, 프로젝트 단위로 자료를 묶어 두는 방식 | 긴 문서와 여러 파일을 한 번에 다루는 작업에 무게 | 한 번에 몇 개 파일을 넣어야 하는가 |
| 정보 습득 | 대화 중 검색을 붙여 최신 정보를 가져옴 | 검색과 외부 연결을 함께 씀 | 답의 근거가 최신 정보여야 하는가 |

표만 보면 둘이 거의 같아 보입니다. 실제 차이는 **연결하는 방식**에서 납니다. ChatGPT는 서비스 안에서 앱과 기능을 조립하는 쪽으로 자랐고, Claude는 개발 도구와 외부 데이터에 붙는 규격을 열어 두는 쪽으로 자랐습니다. 그래서 "회사 시스템에서 자료를 가져와 정리하는 일"을 맡길 때는 어떤 연결이 이미 준비돼 있는지가 선택을 가릅니다.

여기에 하나 더 붙습니다. 두 도구 모두 같은 모델을 여러 방식으로 제공합니다. 웹 화면, 데스크톱 앱, 모바일 앱, API가 각각 다른 한도와 다른 기능을 가집니다. 같은 서비스인데 웹에서는 되는 파일 업로드가 API에서는 안 되는 식의 차이가 흔합니다. 비교할 때는 어느 서비스인가가 아니라 **어느 통로로 쓸 것인가**까지 정해야 합니다.

## 작업별로 먼저 손이 가는 쪽

아래 표는 "이 작업이면 무조건 이 도구"가 아니라, **처음 시험해 볼 순서**입니다. 실제 결론은 5절의 자체 테스트로 정하는 편이 정확합니다.

| 작업 | 먼저 시도 | 그렇게 보는 이유 | 확인할 것 |
| --- | --- | --- | --- |
| 긴 계약서·논문 통독 | 파일을 여러 개 넣을 수 있는 쪽 | 근거 위치를 함께 물어야 하므로 입력 용량이 관건 | 인용한 페이지·조항이 실제로 맞는지 |
| 코드 수정·리팩터링 | 저장소 단위면 코딩 에이전트, 한 파일이면 대화형 | 변경 범위를 좁히고 테스트로 확인할 수 있는 쪽이 안전 | 테스트 통과 여부, 바뀐 파일 목록 |
| 한국어 보고서 초안 | 둘 다, 같은 자료로 비교 | 문체 취향이 갈리는 영역이라 실측이 빠름 | 내가 고친 문장 수 |
| 표·CSV 변환 | 둘 다 | 형식을 지정하면 둘 다 잘함 | 행 수가 보존됐는지 |
| 최신 정보 조사 | 검색이 붙은 대화 | 출처 링크를 받아 원문 대조가 가능 | 링크가 실제로 열리고 내용이 맞는지 |
| 반복 자동화·외부 연동 | 연결 방식이 열려 있는 쪽 | 권한과 실패 처리까지 설계해야 함 | 어떤 계정 권한으로 붙는지 |
| 이미지·도표 해석 | 둘 다 | 숫자 오독이 가장 흔한 실패 | 원본 표와 숫자 대조 |
| 회의록 정리 | 긴 전사 파일을 넣을 수 있는 쪽 | 입력이 길고 화자 구분이 필요 | 화자 이름이 뒤바뀌지 않았는지 |
| 번역·톤 조정 | 둘 다 | 용어집을 고정하면 차이가 줄어듦 | 용어가 끝까지 일관적인지 |
| 사내 문서 질의 | 검색 연동이 가능한 쪽 | 권한과 보관 정책이 먼저 | 학습에 쓰이지 않는 설정인지 |

이 표에서 눈에 띄는 것은, 절반 이상의 작업에서 "둘 다"가 답이라는 점입니다. 실제로 두 도구의 차이는 평균 성능보다 **실패하는 방식**에서 더 크게 갈립니다. 한쪽은 형식을 어기고, 다른 쪽은 없는 내용을 그럴듯하게 채웁니다. 어느 실패가 내 업무에서 더 비싼지가 선택 기준이 됩니다.

## 먼저 시도할 쪽을 정하는 세 가지 질문

표를 외우기보다 이 세 질문을 먼저 던지면 대개 답이 나옵니다.

1. **입력이 긴가, 여러 파일인가**. 한 번에 넣을 수 있는 자료의 양이 정해져 있습니다. 자료를 잘라 넣어야 한다면, 잘린 조각 사이의 맥락을 누가 이어 주는지가 중요해집니다.
2. **결과를 코드나 시스템에 바로 넣는가**. 사람이 읽고 끝나는 문서라면 어느 쪽이든 됩니다. 반면 결과가 자동화 파이프라인에 들어간다면 출력 형식을 지키는 능력과 API 사용 조건이 결정적입니다.
3. **틀렸을 때 누가 확인하는가**. 검증 비용이 큰 업무일수록 "그럴듯한 오답"을 덜 만드는 쪽을 골라야 합니다. 반대로 내가 쉽게 확인할 수 있는 업무라면, 빠르게 초안을 주는 쪽이 낫습니다.

세 번째 질문은 자주 빠뜨리는데, 실제 만족도를 가장 크게 가릅니다. 답을 검증하는 방법 자체는 [AI 답변 검증 루틴](/posts/verify-ai-answers/)에 따로 정리해 두었습니다.

## 비교표 대신 내 업무 3개로 재는 법

이제 직접 잽니다. 준비물은 실제 업무 세 개와 30분입니다. 중요한 것은 **두 도구에 완전히 같은 입력과 같은 프롬프트를 넣는 것**입니다.

| 라운드 | 무엇을 넣나 | 무엇을 보나 |
| --- | --- | --- |
| 1라운드 | 가장 자주 하는 업무 하나 | 결과를 쓰기까지 내가 고친 글자·줄 수 |
| 2라운드 | 경계 사례 하나 (표가 섞인 문서, 일부러 오류를 넣은 코드) | 틀렸을 때 어떻게 틀리는지 |
| 3라운드 | 2주 뒤 같은 과제 재실행 | 업데이트로 결론이 바뀌는지 |

1라운드는 "잘 만드는가"를 보고, 2라운드는 "망가질 때 어떻게 망가지는가"를 봅니다. 실무에서 더 중요한 쪽은 2라운드입니다. 잘 만든 결과는 어느 도구나 비슷하지만, 실패의 모양은 꽤 다릅니다.

기록은 아래 형식으로 남기면 됩니다. 표보다 문장이 편하면 문장으로 적어도 됩니다.

```text
[과제] 11월 실적 보고서 초안 (표 3개, 1,800자)
[도구] A: 웹 대화 / B: 웹 대화

정확성 (숫자·사실 오류 개수)      :
형식 준수 (표·항목·길이)  0~5     :
수정량 (내가 고친 문장 수)        :
소요 시간 (첫 요청~쓸 만한 상태)  :
한국어 자연스러움  0~5            :
실패 방식 (어떻게 틀렸나)         :
```

수정량을 세는 것이 핵심입니다. "느낌이 좋다"는 판단은 다음 날 바뀌지만, 고친 문장 수는 바뀌지 않습니다. 세 라운드를 마치면 대개 업무별로 답이 하나씩 나오고, 그 답은 비교 글이 새로 올라와도 잘 흔들리지 않습니다.

## 한쪽으로 초안, 다른 쪽으로 검토

두 도구를 배타적으로 고르는 대신 나눠 쓰는 방법도 있습니다. 오히려 이쪽이 실무에서 더 자주 이깁니다. 서로 다른 모델은 서로 다른 곳에서 틀리기 때문에, 한쪽의 결과를 다른 쪽에 검토시키면 내가 놓친 것을 잡아 주는 경우가 많습니다.

**첫째, 초안은 한쪽에서, 검토는 다른 쪽에서**. 검토를 맡길 때는 고쳐 쓰지 말고 지적만 하도록 제한해야 합니다.

```text
아래 글을 고쳐 쓰지 말고 검토만 해라.
1) 사실이나 숫자가 틀렸거나 출처가 필요한 문장
2) 빠진 조건이나 예외
3) 한국어가 어색한 문장 (수정 전 → 수정 후)

각 항목은 원문을 그대로 인용하고, 항목마다 3개까지만.
문제가 없다고 판단한 항목은 "이상 없음"이라고만 써라.
```

**둘째, 코드는 만드는 쪽과 리뷰하는 쪽을 나눕니다**. 코딩 에이전트가 만든 변경을 다른 도구에 붙여 넣고, 버그와 빠진 테스트만 찾게 합니다. 같은 도구에 다시 물으면 자기 답을 변호하는 답이 나오기 쉽습니다.

**셋째, 조사와 작성을 나눕니다**. 최신 정보가 필요한 조사는 검색이 붙은 쪽에서 하고, 그 결과를 붙여 긴 문서를 쓰는 일은 문장이 마음에 드는 쪽에서 합니다. 이때 조사 결과에 출처와 확인 날짜를 함께 적어 넘겨야 나중에 검증할 수 있습니다.

<Callout type="warn" title="두 도구가 같은 실수를 하면 도구 문제가 아닙니다">
한쪽에서 어색한 답을 받고 다른 쪽에 똑같이 물었는데 비슷하게 어긋난다면, 원인은 도구가 아니라 지시문이나 자료 쪽일 가능성이 큽니다. 조건이 빠진 요청, 예시 없는 형식 요구, 서로 충돌하는 지시가 대표적입니다. 이때 도구를 바꾸는 대신 [프롬프트 5가지 구조](/posts/prompt-structure-5/)와 [예시·출력 제약](/posts/few-shot-output-constraints/)을 먼저 점검하세요.
</Callout>

## 돈과 한도: 숫자 대신 확인할 항목

요금과 한도는 이 글에서 가장 빨리 낡는 부분입니다. 그래서 금액을 적지 않고, **결제 전에 반드시 확인해야 할 항목**만 정리합니다.

| 확인 항목 | 왜 중요한가 | 어디서 보나 |
| --- | --- | --- |
| 요금제 이름과 포함량 | 이름이 바뀌면 내가 아는 조건과 달라짐 | 공식 요금 페이지 |
| 메시지 한도의 산정 방식 | 시간당인지 일정 시간 구간인지에 따라 업무 시간에 걸림 | 도움말의 한도 설명 |
| 긴 문서 처리 한도 | 파일 크기와 개수 제한이 업무 가능 여부를 가름 | 모델·파일 업로드 도움말 |
| 팀 기능과 권한 | 공유 범위, 감사 로그, 관리자 설정 | 팀·비즈니스 요금 안내 |
| 데이터 학습·보관 정책 | 민감한 자료를 넣어도 되는지 결정 | 개인정보·데이터 설정 문서 |
| API와 구독의 분리 | 자동화에 API를 쓰면 별도 과금일 수 있음 | API 가격표 |
| 결제 통화와 환불 조건 | 연간 결제 시 차이가 큼 | 결제·환불 정책 |

<Callout type="warn" title="무료로 보이는 표현에는 조건이 붙습니다">
비교 글의 요금표를 그대로 믿고 결제했다가 한도에 걸리는 일이 흔합니다. 특히 "무제한"에 가까운 표현은 보통 속도 제한이나 모델 제한이 함께 붙습니다. 결제 화면에서 실제 청구 금액과 갱신 주기를 확인하고, 가능하면 월 단위로 먼저 써 본 뒤 연간으로 바꾸는 편이 안전합니다.
</Callout>

## 비교가 무너지는 지점

직접 재 볼 때도 아래 함정에 빠지면 결론이 엉뚱해집니다.

| 함정 | 증상 | 피하는 법 |
| --- | --- | --- |
| 한 번의 시험으로 결론 | 첫 답이 운 좋게 잘 나옴 | 같은 과제를 세 번 반복해 평균을 봄 |
| 긴 대화에 계속 이어 붙임 | 뒤로 갈수록 앞 내용을 잊음 | 과제마다 새 대화로 시작 |
| 파일 첨부와 본문 붙여넣기를 섞음 | 같은 자료인데 결과가 다름 | 한 가지 방식으로 통일 |
| 프롬프트를 그대로 복사 | 한쪽에 맞춘 지시가 다른 쪽에서 어긋남 | 도구별로 한 번씩 다듬어 줌 |
| 개인 요금으로 팀 업무 평가 | 권한·공유 기능이 빠져 있음 | 실제 쓸 요금제로 시험 |
| 최신 정보를 학습 지식으로 판단 | 오래된 내용을 확신 있게 말함 | 검색 사용 여부와 출처를 확인 |

세 번째 함정은 의외로 자주 걸립니다. 파일로 넣은 표와 본문에 복사한 표는 잘리는 방식이 다릅니다. 파일이 잘려서 일부 행이 빠졌는데도 도구의 성능 문제로 오해하기 쉽습니다. 표를 넣을 때는 행 수를 함께 적어 주고, 결과에서 행 수가 유지됐는지 세어 보세요.

## 자료를 넣기 전에 한 번 멈추기

비교 시험을 하다 보면 실제 업무 자료를 그대로 넣게 됩니다. 계약서, 인사 기록, 고객 문의, 매출 표가 그대로 들어가면 두 서비스의 서버에 남습니다. 시험용으로는 구조만 같은 가짜 자료를 만드는 편이 좋습니다. 실제 표의 머리글과 형식은 그대로 두고 값만 다른 숫자로 바꾸면, 대부분의 비교는 그대로 진행됩니다.

무엇을 지우고 무엇을 남길지, 설정에서 어디를 확인해야 하는지는 [AI에 넣기 전 데이터 가림 기준](/posts/data-masking-before-ai/)에 정리해 두었습니다.

## 5분 체크리스트

- [ ] 비교할 내 업무 세 개를 골랐는가
- [ ] 두 도구에 같은 입력과 같은 프롬프트를 넣었는가
- [ ] 결과를 쓰기까지 고친 문장·줄 수를 셌는가
- [ ] 일부러 어려운 사례로 실패 방식을 확인했는가
- [ ] 요금·한도를 공식 페이지에서 확인했는가
- [ ] 실제로 쓸 요금제(개인·팀)로 시험했는가
- [ ] 민감한 자료는 가짜 자료로 바꿨는가
- [ ] 2주 뒤 다시 재 볼 날짜를 잡았는가

## 정리

ChatGPT와 Claude 중 무엇을 쓸지는 남이 정해 줄 수 있는 문제가 아닙니다. 두 도구의 구조 차이를 알고, 내 업무 세 개로 직접 재고, 필요하면 한쪽 초안을 다른 쪽이 검토하게 하면 됩니다. 이렇게 하면 새 모델이 나와도 비교 글을 다시 읽지 않고, 새 과제만 같은 방식으로 재면 됩니다.

오늘 하나만 한다면, 지금 가장 자주 하는 업무 하나를 골라 두 도구에 같은 프롬프트로 넣고 고친 문장 수를 세어 보세요. 그 숫자 하나가 어떤 비교 글보다 정확합니다.
