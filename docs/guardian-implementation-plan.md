# 보호자 동의·철회·삭제 구현 상태와 남은 계약

2026-10-20, Asia/Seoul. `children-launch-plan.md`의 만 14세 미만 포함 방침을 유지하며 추가한 서버와 기존 계정용 정보 관리 UI를 정리한다. 서버 코드·테스트용 서명 검증과 실제 보호자 확인 서비스 연결은 구별한다. 이 문서는 법률 검토 완료, 운영 준비 완료, 보호자 동의 실증을 뜻하지 않는다.

## 1. 현재 구현 범위

| 영역 | 구현된 것 | 운영 전 남은 것 |
|---|---|---|
| 보호자 요청 | 기존 인증 계정이 시작하는 요청, 토큰·nonce 해시, 고정 5일 만료, 요청 재발급·거부·정리 | 실제 성인 보호자의 최초 가입·재인증 경로, 요청·동의 화면 |
| 외부 확인 | 고정 RS256 공개키와 발급자·수신자·요청·계정·nonce 검증, 신원·성인 여부·관계·동의 항목·문구 버전의 개별 검사 | 제공자 선정·계약·실제 공개키 및 정책 구성·실계정 확인 |
| 아동 연결 | 기존 `pending` 계정에 대한 내부 일회용 연결, 기존 플레이어·다른 가족·재사용 차단 | 실제 동의 대상 아동과 로그인 대상을 일치시키는 신뢰된 가입 어댑터 |
| 권리 행사 | 본인 기록 다운로드, 서버 확인 아동 목록·상태·자료 내보내기·철회·삭제 접수와 확인 UI | 닫힌 본인 계정의 별도 재인증·후속 권리 행사 UI, 정정 절차 |
| 게임 차단 | 계정 허가를 인증과 SQL 쓰기 시점에 확인, 철회·삭제 계정의 게임·공개 순위 노출 차단 | 실운영 부하·DB·복구 환경 검증 |
| 삭제 | 두 계정 루트와 관련 데이터의 원자적 삭제, 재시도 가능한 접수, 최소 재생성 차단 기록 | 운영자가 검토한 보존 정책, 실제 백업·복구 후 재삭제 체계 |
| 유지 관리 | 방문과 독립적으로 실행할 수 있는 로컬 1회 정리 명령 | 운영 스케줄러·실패 알림·누락 감지·기한 내 삭제 증거 |

독립 서버는 `HARU_REGISTRATION_OPEN=false`를 강제한다. 보호자 상태는 `guardianReady:false`, `enrollmentOpen:false`다. 성인·아동의 안전한 최초 진입 경로가 완성되지 않아 독립 서버는 `loginEnabled:false`도 강제한다. OAuth 키가 채워져도 `/start`, `/callback`으로 신규 정보를 수집하는 흐름을 열지 않는다. 기존 Sites 인증 경로와 이 독립 서버 정책을 혼동하지 않는다.

## 2. 동의 전 수집을 제한한 요청

현재 요청은 **이미 인증된 보호자 계정이 먼저 시작**한다. 요청 생성 API는 본문에 아동 이름·연락처·소셜 식별자·닉네임을 받지 않는다. 보호자의 이름·연락처를 새로 받는 필드도 없다. 기존 내부 보호자 계정 ID와 무작위 요청 식별자, 최초 생성 시각·고정 만료 시각, 문구 버전, 토큰·nonce 해시만 저장한다. 실제 제공자 어댑터 없이 임의의 성공 결과를 생성하지 않는다.

요청 생성·재발급 응답의 평문 토큰과 nonce는 해당 흐름에서만 다루며 목록 조회에는 포함하지 않는다. 증빙 원문 JWT, 제공자 주체 원문, 연락처, 개인정보를 로그에 기록하지 않는다. 이미 로그인했다는 사실은 신원·성인·법정대리인 관계 확인을 대신하지 않는다.

## 3. 증빙 검증과 아동 연결의 경계

`server/guardian-service.mjs`는 고정 공개키로 서명을 확인한 뒤 `iss`, `aud`, `sub`, `jti`, `iat`, `exp`, 요청 ID, 보호자 계정 ID, nonce를 검사한다. 신원 확인, 성인 확인, 법정대리인 관계 확인, 명시적 동의는 모두 별도의 참이어야 한다. 동의 항목은 지정된 세 항목과 정확히 일치하고, 문구 버전은 해당 요청 및 현재 서버 설정과 같아야 한다. 상세 제공자 계약은 [운영 설명](privacy-operations.md)을 따른다.

승인은 원자적 배치로 확정한다. 동일 증빙의 중복 콜백은 같은 승인으로 수렴하고, 다른 요청에 같은 증빙 식별자를 재사용할 수 없다. 서명 확인 후 DB 대기 중 만료되는 경우도 SQL의 DB 시각 검사로 거절한다. 요청 토큰 재발급은 원래 생성 시각·5일 기한을 변경하지 않는다.

`bindChild`는 HTTP로 노출하지 않은 내부 메서드다. 활성 플레이어가 없는 기존 `pending` 계정을 한 번 활성화할 수 있지만 **실제 아동의 신원과 법정대리인 관계를 이 함수만으로 확인하지 않는다.** 현재 증빙 계약은 요청·보호자에 묶여 있으며 아동의 실명/식별 정보를 담지 않는다. 미래의 신뢰된 가입 어댑터가 제공자 확인 대상 아동과 서버가 만든 대기 계정이 같은 대상임을 별도로 확인해야 한다. 클라이언트가 임의의 아동 ID를 보내 연결하게 해서는 안 된다. 이 어댑터가 없으므로 실제 아동 가입은 계속 닫혀 있다.

## 4. 저장 상태와 경쟁 처리

새 `drizzle/0004_guardian_privacy.sql`은 `db/schema.ts`에서 생성했으며 기존 0000~0003 SQL은 변경하지 않는다.

| 테이블 | 목적 |
|---|---|
| `guardian_requests` | 대기·승인 요청, 토큰·nonce 해시, 최초 시각과 고정 만료 |
| `guardian_consents` | 최소 증빙 해시와 주체 해시, 동의 항목·버전, 승인·철회 시각 |
| `guardian_links` | 보호자–아동 연결과 활성·철회 상태 |
| `privacy_account_controls` | `pending`, `active`, `withdrawn`, `deletion_pending`, `deleted` 허가 상태 |
| `privacy_deletion_jobs` | 중복 접수 방지용 작업 ID·상태·시각·요청 주체 해시 |

연결 완료 시 사용한 요청은 제거하고 최소 동의 증빙과 관계를 남긴다. 거부 시 대기 요청과 아직 연결되지 않은 증빙을 즉시 제거한다. 기한이 지난 미연결 요청·증빙은 유지 관리 실행에서 제거한다. 거부·만료 기록을 남기기 위해 개인정보를 다시 복사하지 않는다.

계정 차단 행은 인증 계정 삭제와 함께 사라지지 않도록 외래키 cascade를 두지 않는다. 기존 레거시 계정처럼 차단 행이 없으면 게임 접근은 허용하되, 차단 행이 `active`가 아니거나 인증 계정이 비활성화되어 있으면 차단한다. 게임의 프로필 생성·답안·구매·정산도 실제 SQL 변경 시점에 이를 확인한다. 인증 조회가 끝난 뒤 철회된 요청이 대기 중인 쓰기를 완료하거나 프로필을 재생성하지 못하도록 한다.

## 5. 권리 행사와 삭제 상태

독립 HTTP API는 최근 15분 이내 발급된 불투명 세션을 확인한다. 본인 ID는 서버가 세션에서 결정하고, 아동 ID를 지정한 권리 요청은 해당 보호자 관계를 다시 검사한다. 상태 조회에서 받은 `accountContext`를 POST와 아동·보호자 GET 목록의 `X-Haru-Account`로 확인하며 동일 출처·본문 필드·용량·호출 수를 제한한다. HTTP에서 검증한 세션 해시를 서버 내부 증거로 전달하고, 최종 조회·쓰기 시 SQL에서도 동일 계정·세션·철회 여부·만료·최근 인증 기한을 다시 확인한다. 처음 인증을 통과했어도 처리 대기 중 로그아웃하거나 기한을 넘기면 진행할 수 없다.

철회나 삭제 접수는 게임 접근을 닫고 세션 및 관련 OAuth 진행 상태를 취소한다. 어린이의 연결 상태가 철회되어도 인증된 보호자는 권리 행사를 계속할 수 있다. 관리해야 할 활성·철회 아동이 남아 있는 보호자 계정의 철회·삭제는 먼저 차단한다.

본인이 철회하면 자신의 기존 세션도 취소된다. **닫힌 본인 계정이 다시 본인임을 확인하고 후속 권리를 행사하는 경로·화면은 아직 없으며 `selfRecoveryReady:false`다.** 서버 내부 메서드가 본인 ID를 처리할 수 있다는 이유로 사용자용 재인증이 완성되었다고 보지 않는다.

삭제 접수와 실제 삭제는 별개다. 검토한 서버 정책이 없으면 `deletion_pending` 상태로 게임·인증을 차단한 뒤 자료를 보관한다. 정책을 갖춘 유지 관리만 현재 DB에서 게임·인증·보호자 자료를 삭제할 수 있다. 완료 상태의 범위는 `live-database`이며 백업 삭제 완료를 의미하지 않는다. 최소 차단 행과 요청 주체 해시를 포함한 접수 기록은 현재 자동 만료시키지 않는다. 이들 기록의 장기 보존 기간·정리 방법도 아직 운영 정책으로 확정되지 않았다.

## 6. 운영 전 추가해야 할 것

1. 실제 성인 최초 가입·재인증, 제공자 검증, 대상 아동 연결을 하나의 승인 흐름으로 통합한다.
2. 안내 화면을 실제 제공자 동의 요청·확인·아동 연결로 연결하고, 닫힌 본인 계정의 별도 권리 행사 경로를 구현한다. 기존 계정용 정보 관리 화면은 아래 범위까지 구현되어 있다.
3. 아동·보호자 자료, 차단 행, 접수 기록, 백업 각각의 보존·삭제·복원 정책을 검토하고 설정한다.
4. 방문과 무관한 운영 스케줄러를 연결하고, 5일 기한을 넘기기 전 정리가 실제 수행되도록 실행 주기·여유 시간·재시도·경보를 검증한다. 현재 1회 로컬 명령은 이를 대신하지 않는다.
5. 실제 제공자 왕복, 운영 DB, 모바일 화면, 가족별 권한, 동시 철회, 백업 복원 후 재삭제를 검증한다.

로컬 검증 파일은 `tests/guardian-service.test.mjs`, `tests/account-lifecycle.test.mjs`, `tests/privacy-integration.test.mjs`다. 서명 검증은 테스트용 키와 실제 JWT 검증, 저장소 검증은 실제 SQLite 트랜잭션을 사용한다. 전체·HTTP 최종 결과는 별도 검증 기록에 남기며, 이 문서에서 진행 중인 검사 결과를 완료로 추정하지 않는다.

## 7. 기존 계정용 정보 관리 화면

`#privacy`에 본인 기록 다운로드와 서버가 확인한 아동 목록·상태·내보내기를 연결했다. 아동 철회·삭제 요청은 대상과 영향의 확인창을 거치며, 접수 성공과 실제 삭제 완료를 구분한다. 정책이 없어 처리가 대기 중이면 완료로 표시하지 않는다. 응답이 끊기거나 불분명할 때 변경 요청을 자동 재전송하지 않고 현재 상태 조회로 확인한다.

화면은 상태 응답의 공개 `playerId`를 현재 게임 계정과 대조하고, 세션 문맥을 모든 민감한 목록·변경·내보내기 요청에 묶는다. 다운로드 직전에도 문맥과 선택 아동을 확인한다. 탭이 숨겨지거나 화면·계정이 바뀌면 개인 목록·확인창·대기 요청을 지우며, 이전 응답으로 다시 표시하지 않는다. 브라우저 저장소에 보호자 정보나 수동 세션 토큰을 보관하지 않는다.

자기 탈퇴·삭제 버튼은 아직 사용할 수 없으며 `selfClosure:false`, `selfRecoveryReady:false`를 유지한다. `#guardian`은 준비 절차만 설명하고 실제 동의·개인정보를 받지 않는다. 준비 중인 기능을 동작하는 것처럼 보이는 가짜 성공·연결로 대신하지 않는다.

앱 내 데스크톱 854×801 브라우저에서 로그인 전 두 화면·버튼 잠김·전환을 확인했고 콘솔 경고·오류는 없었다. 실제 기기와 로그인한 실계정의 관리 UI는 미검증이다. 최신 자동 검사·빌드 결과는 [검증 기록](codex-verification-2026-10-20.md)을 따른다.
