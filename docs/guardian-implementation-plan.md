# 보호자 동의·철회·삭제의 다음 구현 계약

2026-10-20 Codex 후속 정리. 이 문서는 기존 `children-launch-plan.md`에서 확정한 제품 요구를 구현 단위로 나눈 것이다. 아래 DB·API·외부 확인·예약 작업은 아직 구현하지 않았다. 법률 검토 완료나 실제 보호자 확인 성공을 뜻하지 않는다. 운영 전 공식 조건을 다시 확인한다.

## 1. 동의 전 단계부터 분리

로그인 전 연령 경로를 안내한다. 어린이 경로에서는 보호자 요청에 필요한 최소 성명·연락처 외에 아동 소셜 식별자·닉네임·성적을 수집하지 않는다. 이 단계에서 OAuth 시작이나 게임 계정을 만들지 않는다. 성인의 자체 로그인 성공을 법정대리인 관계 확인으로 취급하지 않는다.

먼저 외부 확인 어댑터의 계약을 만든다. 신원 확인, 법정대리인 관계, 동의한 항목·문구 버전은 서로 다른 검증 결과로 받는다. 실제 제공자 서명과 요청 대상을 검증하기 전에는 승인 결과를 반환할 수 없게 한다. 확인 링크 클릭만으로 상태를 승인으로 바꾸지 않는다. 제공자를 선택하기 전 모의 구현은 테스트 전용으로 한정한다.

## 2. 새 SQL 마이그레이션과 최소 상태

예정 테이블은 동의 대기 요청, 확정 동의 증빙, 보호자–아동 관계, 권리 행사 처리 작업이다. 기존 0000~0003 SQL은 고치지 않고 `db/schema.ts`와 새 생성 마이그레이션을 함께 검토한다.

- 대기 요청: 무작위 요청 ID, 보호자 최소 연락 정보, 최초 수집 시각, 고정 만료 시각, 일회용 토큰의 해시, 동의 문구 버전, 처리 상태. 평문 토큰·비밀값은 보관하지 않는다. 개인정보 암호화·키 관리·서비스 로그 보관을 실제 구성과 함께 결정한다.
- 확정 동의: 검증 방법과 최소 증빙 참조, 확인된 주체·관계, 동의 항목·문구 버전, 승인/철회 시각. 이메일 일치로 계정이나 가족을 연결하지 않는다.
- 계정 허가: 동의와 로그인 연결 대상을 서버가 한 번 소비하는 승인으로 묶는다. 클라이언트가 계정 ID를 지정해서 연결할 수 없게 한다.
- 상태 전이: 대기 → 승인 또는 거부/만료, 승인 → 연결 → 활성, 활성 → 철회/삭제 진행 → 삭제 완료. 만료된 요청과 이미 소비된 승인은 다시 활성화할 수 없다.

## 3. 중복·경쟁 처리

조건부 업데이트와 원자적 배치로 요청 상태·동의·계정 연결을 함께 확정한다. 중복 콜백은 같은 결과로 수렴하고 다른 계정에 승인을 재사용할 수 없어야 한다. 재발급·발송 재시도는 최초 수집 시각과 만료 시각을 바꾸지 않는다.

기존 게임 서비스는 첫 조회 시 프로필을 생성한다. 따라서 탈퇴·철회 상태를 인증 해석 시점에만 확인해서는 부족하다. 진행 중인 답안·구매가 동의 철회 후 커밋되거나 삭제된 플레이어를 다시 만드는 경쟁을 막도록 **게임의 원자적 쓰기 단계에서도 현재 계정 허가를 확인하는 DB 조건**을 추가한다. 보호자 권리 행사 경로는 게임 차단과 별개로 유지한다.

## 4. 철회와 권리 행사

보호자 재확인 → 서버 관계 조회 → 해당 아동에 대한 열람·정정·내보내기·철회·삭제 권한 검사 순서를 지킨다. 다른 가족 ID를 넣거나 예전 세션을 재사용해 접근하지 못해야 한다.

철회 시 신규 플레이·구매·공개 노출을 즉시 차단하고 모든 게임 세션과 진행 중인 인증 흐름을 철회한다. 별도 확인 경로로 필요한 권리 행사를 계속 처리한다. 삭제는 게임 프로필, 시도, 결과, 원장, 영수증, 주간 보상, 속도 제한, 로그인 연결, 세션을 실제 외래키와 대조한다. 주간 순위의 이미 확정한 통계·익명화 범위와 별도 보존 근거는 운영 정책과 합의한 뒤 적용한다.

게임 플레이어와 인증 계정의 내부 식별자는 연결돼 있어도 서로 자동 cascade 된다고 가정하지 않는다. 삭제 작업 ID와 완료 상태는 재시도할 수 있어야 하고, 실데이터 삭제 전에 백업 보유·복원 시 재삭제 절차까지 연결한다. 미결정한 보존 기간을 임의로 영구 보관이나 즉시 전량 삭제로 확정하지 않는다.

## 5. 방문과 무관한 예약 삭제

기존 계획의 제품 기준인 거부 시 즉시 삭제, 미확인 요청은 최초 수집일부터 5일 이내 삭제를 구현한다. 방문 요청에 붙는 정리만으로 대신하지 않는다. 예약 작업은 만료 전 여유 있게 실행하고 중단·재시도·실패 감지와 알림을 운영 환경에 연결한다. 재발급이 기한을 연장하지 않도록 고정된 원래 시각으로 조회한다. 운영 완료를 표시하려면 예약 실행과 실제 삭제 증거가 있어야 한다.

## 6. 구현 후 통과시킬 검증

| 검증 | 필요한 증거 |
|---|---|
| 동의 전 OAuth·계정 생성 차단 | HTTP 경로와 실제 SQL 검사 |
| 서명·주체·관계가 다른 확인 결과 차단 | 실제 서명 검증 및 거부 사례 |
| 중복·만료·재발급·동시 철회 | 조건부 배치와 두 요청을 겹친 테스트 |
| 가족 간 접근 차단 | 별도 보호자/아동/세션 조합별 API 검사 |
| 철회와 게임 쓰기 경쟁 | 대기 중 답안·구매가 철회 후 커밋되지 않음 |
| 거부·5일 기한 삭제 | 고정 시계 테스트와 운영 예약 작업 증거 |
| 탈퇴·복원 후 재생성 방지 | 세션·공개 순위·관계·DB 삭제 및 복원 절차 |

이 단계가 끝나기 전에는 독립 API의 가입 차단과 `guardianReady=false`를 유지한다. 호스팅·외부 확인 서비스·실제 비밀 설정·보존 정책이 필요한 항목과 비밀값 없이 가능한 구현/테스트를 구분해 이어간다.
